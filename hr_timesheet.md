# Timesheets — What a Timesheet Really Is, When Lines Are Created, and Where the Money Goes

> **Modules:** `hr_timesheet` (community core) + `timesheet_grid` (enterprise: grid UI, timer, validation) + `project_timesheet_holidays` (Time Off bridge) | **Path:** [`addons/hr_timesheet/`](../addons/hr_timesheet/)
> Related: [`geo_payroll.md`](geo_payroll.md), [`work_entries.md`](work_entries.md), [`payroll_wage_types.md`](payroll_wage_types.md)

## What It Is

There is no "timesheet" model. A timesheet is an **`account.analytic.line` whose `project_id` is set** — the same model that carries every analytic (cost-accounting) entry in Odoo. `hr_timesheet` extends it with `project_id`, `task_id`, `employee_id`, and the timesheet behaviors. One line = one person / one date / one project(+task) / `unit_amount` hours / a money `amount`.

Because timesheets live in the analytic world, their money is **project cost accounting** — they never touch payroll, journals, or salaries by default.

## When Lines Are Created — every path

| # | Trigger | When exactly | Marker fields |
|---|---|---|---|
| 1 | Manual entry — task form "Timesheets" tab, Timesheets app grid/list | On save of the row | none |
| 2 | Grid timer (enterprise) | Started/stopped from the grid or task; the line's `unit_amount` is filled from the timer [Likely: line created at timer start with 0h, updated at stop] | timer fields |
| 3 | **Employee leave validation** (`project_timesheet_holidays`) | `hr.leave._validate_leave_request()` → `_generate_timesheets()` → `sudo().create()` — one line per working day of the leave, on the company's internal "Time Off" project/task ([hr_leave.py:13-66](../addons/project_timesheet_holidays/models/hr_leave.py#L13)) | `holiday_id` |
| 4 | **Public holiday creation** (same bridge) | Creating a `resource.calendar.leaves` generates internal-project lines for affected employees ([resource_calendar_leaves.py](../addons/project_timesheet_holidays/models/resource_calendar_leaves.py)) | `global_leave_id` |
| 5 | Field Service / Helpdesk timers | Variants of #1/#2 on their tasks | — |
| 6 | (planned custom) `geo_payroll` OT-approval bridge | Would create a draft line per approved OT log — off in release 1 | `work_log_id` |

Paths 3 and 4 are the reason a payroll integration must **never** pay "all timesheets": leave and holiday lines are bookkeeping noise generated by sudo, not worked time.

## The Money — cost is booked immediately, at `hourly_cost`

On every create/write touching `unit_amount`, `employee_id`, or `account_id`, `_timesheet_postprocess_values()` recomputes:

```text
amount = − unit_amount × employee.hourly_cost        (converted to company currency)
```

([hr_timesheet.py:443-471](../addons/hr_timesheet/models/hr_timesheet.py#L443), cost source [hr_timesheet.py:496-498](../addons/hr_timesheet/models/hr_timesheet.py#L496))

- **Negative** = a cost on the project's analytic account (`account_id`, auto-filled from the project via `_timesheet_preprocess_get_accounts`, [hr_timesheet.py:416](../addons/hr_timesheet/models/hr_timesheet.py#L416)).
- `hourly_cost` lives on the employee's HR Settings tab — it is a **costing** rate (what an hour of this person costs the company), deliberately not the payroll wage.
- Analytic only: no journal entry, no payable, no payslip. It feeds project profitability reports and, on billable projects, invoicing quantities.

## Validation (enterprise `timesheet_grid`)

Managers validate periods in the grid → `validated=True` per line + `employee.last_validated_timesheet_date` advances, locking employees out of editing anything on or before that date. Validation is the natural "manager approved these hours" gate — which is why the planned `geo_payroll_timesheet` bridge pays only validated lines.

## What Consumes Timesheets by Default

| Consumer | What it reads |
|---|---|
| Project profitability | the negative `amount` (costs) per analytic account |
| Sales invoicing (service products invoiced on timesheets) | `unit_amount` as delivered quantity; billable lines get `so_line` |
| Timesheet reports / grid | hours |
| **Payroll** | **nothing — no native link exists** (verified across `hr_payroll`; `work_entry_source` has no timesheet option). Hourly-workers-from-timesheets is always a customization |

## Where to See the Project Cost

| Surface | Path | What you get |
|---|---|---|
| Timesheets reporting (no accounting rights needed) | Timesheets app → Reporting → group by Project, measure **"Timesheet Costs"** — the `amount` field exposed in the pivot/graph ([hr_timesheet_views.xml:69](../addons/hr_timesheet/views/hr_timesheet_views.xml#L69)) | Cost per project/employee/month |
| Project Dashboard | Project app → open project → **Dashboard** → Profitability block (base: [project_project.py:1048](../addons/project/models/project_project.py#L1048); `sale_timesheet` breaks timesheet costs out per billing type) | Revenues vs costs of the project |
| Analytic Items (raw ledger) | Accounting → Analytics → Analytic Items, filter by the project's analytic account | Every individual line, the negative amounts themselves |

Prerequisite for any of it: the employee's **Hourly Cost** (employee form → HR Settings). If it is 0, every timesheet books a 0.00 cost and all three surfaces show hours but no money.

## Edge Cases & Gotchas

- Leave/holiday lines (`holiday_id` / `global_leave_id`) are created in sudo and can be swept up by validation; regeneration deletes them in sudo without recomputing `last_validated_timesheet_date` — the boundary can lock ordinary timesheets (see [`work_entries.md`](work_entries.md)).
- `unit_amount` is always stored in **hours**, even when the company encodes timesheets in days.
- Changing the employee's `hourly_cost` does not rewrite historical line amounts (recompute fires only on line writes).
- An analytic line without `project_id` is not a timesheet — same table, none of the timesheet logic.
